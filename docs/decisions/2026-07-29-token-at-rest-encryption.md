# ADR-0008: 토큰 저장 암호화는 AES-256-GCM + 전용 키 환경변수

- 기록일: 2026-07-29 12:32
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: [1_spack.md — ENT-03 / POL-05](../../1_spack.md), [2_ddd.md — AGG-03](../../2_ddd.md)
- 관련 plan: [00-ORCHESTRATOR.md — Phase 2 Task 2.2](../../00-ORCHESTRATOR.md)

## 맥락 (Context)

[1_spack.md](../../1_spack.md) ENT-03 은 `token` 을 "**암호화된** 액세스 토큰"으로 규정하고,
POL-05 는 토큰 전문 노출률 0% 를 요구한다. 어떤 알고리즘·키 관리를 쓸지는 명세에 없다.
3_architecture.md 에도 KMS·Vault 같은 키 관리 서비스가 없어, 키는 환경변수로 주입할 수밖에 없다.

## 결정 (Decision)

AES-256-GCM 으로 암호화하고(IV 를 매번 새로 생성해 암호문 앞에 붙임), 키는 전용 환경변수
`CREDENTIAL_ENCRYPTION_KEY`(base64 32바이트)로 분리해 주입한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| AES-256-GCM + 전용 키 환경변수 | 기밀성 + **무결성**을 함께 얻는다(변조 시 복호화 실패). JDK 표준이라 의존성 추가 없음. 키 용도가 분리돼 하나가 유출돼도 다른 것이 안 무너진다 | 키를 잃으면 저장된 토큰을 복호화할 수 없다. 키 로테이션 절차가 별도로 필요 | **채택** |
| AES-CBC | 널리 쓰임 | 무결성 검증이 없어 변조된 암호문을 조용히 복호화한다. 패딩 오라클 위험 | 기각 |
| `JWT_SECRET` 을 암호화 키로 재사용 | 환경변수 하나로 끝 | 용도가 다른 비밀을 겹쳐 쓰면 하나가 유출될 때 피해가 두 배가 된다. JWT 서명 키 로테이션이 곧 토큰 전부 복호화 불가로 이어진다 | 기각 |
| 암호화 없이 평문 저장 | 가장 단순 | ENT-03 명세("암호화된") 정면 위반. DB 유출이 곧 인스타그램 계정 탈취 | 기각 |
| KMS/Vault 도입 | 키 관리가 가장 안전 | 3_architecture.md 에 없는 구성요소 발명. 로컬 무인 실행(Principle 10) 불가 | 기각 |

## 근거 (Rationale)

GCM 을 고른 결정적 이유는 **무결성**이다. CBC 는 DB 의 암호문이 손상·변조돼도 복호화가 "성공"해
쓰레기 토큰을 인스타그램에 보내게 되고, 그러면 원인 추적이 매우 어려워진다.
GCM 은 그 자리에서 예외를 낸다 — 조용한 실패보다 시끄러운 실패가 낫다.

키를 `JWT_SECRET` 과 분리한 것은 용도별 비밀 분리 원칙이다. 두 키의 로테이션 주기와
유출 시 영향 범위가 완전히 다르므로 겹쳐 쓰면 안 된다.

## 영향 (Consequences)

- 긍정: 같은 토큰을 두 번 암호화해도 암호문이 달라진다(IV 매번 생성 — 테스트로 고정).
  변조 시 복호화가 실패한다(테스트로 고정). 키 길이·형식이 틀리면 기동을 거부한다(fail-fast).
- 트레이드오프/비용: **키를 잃거나 바꾸면 기존 `security_credentials` 행을 복호화할 수 없다.**
  그 경우 토큰을 다시 발급(API-05 재호출)해야 한다. `.env.example` 에 이 경고를 명시했다.
- 후속 제약:
  - 새 환경변수가 필수로 추가됐다 — `.env` 에 없으면 서버가 기동하지 않는다.
  - 키 로테이션 절차(기존 암호문 재암호화)는 이번 범위 밖이다. 필요해지면 별도 결정이 필요하다.
  - 오류 메시지에 키 값을 넣지 않는다(길이만 노출 — 테스트로 고정).
