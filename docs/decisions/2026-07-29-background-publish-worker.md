# ADR-0013: 실제 게시는 백그라운드 워커가 수행한다

- 기록일: 2026-07-29 14:31
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: [1_spack.md — API-04 / POL-04](../../1_spack.md), [2_ddd.md — Story-01.2](../../2_ddd.md)
- 관련 plan: [00-ORCHESTRATOR.md — Phase 3 Task 3.1](../../00-ORCHESTRATOR.md)

## 맥락 (Context)

두 가지가 동시에 걸린다:

1. **POL-04** — "API 응답 시간은 3초 이내로 유지되어야 함" (전 시스템 적용).
   그런데 릴스 게시는 영상 업로드 + 인스타그램 인코딩 대기 + 발행으로 수십 초에서 수 분이 걸린다.
   요청 스레드에서 기다리면 POL-04 를 지킬 수 없다.
2. **Story-01.2** — "예약 실행 및 실패 정책". `QueueItem.scheduledAt` 을 저장만 하고
   아무도 실행하지 않으면 "예약 발행"은 동작하지 않는 죽은 기능이 된다.

명세의 API-04 응답이 `201 Created` + `status: "PROCESSING"` 인 것도 같은 그림을 가리킨다 —
"접수했고 처리 중"이라는 뜻이다.

## 결정 (Decision)

API 는 동기 구간에서 검증·등록만 하고 즉시 201 을 반환한다.
실제 4단계 파이프라인은 `@Scheduled` 워커({@code PublishWorker})가 수행한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 스케줄 워커 (폴링) | 예약 실행과 즉시 업로드를 하나의 경로로 처리한다(즉시 업로드 = `scheduledAt=now`). 인스턴스가 죽어도 다음 주기에 회수 가능. 추가 인프라 없음 | 최대 한 주기(10초)의 지연. DB 폴링 비용 | **채택** |
| 요청 스레드에서 동기 처리 | 구현이 가장 단순. 결과를 바로 알려줄 수 있음 | POL-04(3초) 정면 위반. 명세의 `PROCESSING` 상태와 모순. Tomcat 스레드가 수 분씩 점유되어 동시 요청 몇 건에 서비스가 마비된다 | 기각 |
| `@Async` 로 요청 직후 별도 스레드 | 응답은 빠르고 지연도 없음 | 인스턴스가 죽으면 그 작업은 영구히 사라진다(DB 에 "진행 중"만 남음). 예약 발행은 따로 또 구현해야 한다 | 기각 |
| 메시지 큐(Kafka/RabbitMQ) 도입 | 확장성·내구성이 가장 좋음 | 3_architecture.md 에 메시지 브로커가 없다 — 아키텍처에 없는 구성요소 발명. 로컬 실행 부담 증가 | 기각 |

## 근거 (Rationale)

워커 방식이 두 요구를 한 번에 만족시킨다: POL-04 는 동기 구간을 짧게 유지해 지키고,
Story-01.2 의 예약 실행은 같은 워커가 담당한다. `@Async` 를 골랐다면 예약 실행기를
따로 만들어야 했고, 그러면 같은 일을 하는 코드가 두 벌이 된다.

10초 지연은 "예약 발행" 도구의 성격상 문제가 되지 않는다(사용자가 초 단위 즉시성을 기대하는 기능이 아니다).

`fixedDelay`(고정 지연)를 쓴 이유: `fixedRate` 는 이전 주기가 길어지면 다음 주기와 겹쳐
같은 항목을 두 번 집을 수 있다.

## 영향 (Consequences)

- 긍정: API 응답 실측 최대 0.43초(POL-04 여유 있게 충족). 예약 발행이 실제로 동작한다
  (검증에서 워커가 항목을 집어 실패 이력까지 남기는 전 과정을 관측).
- 트레이드오프/비용:
  - 접수와 실제 게시 사이에 최대 10초 지연. 화면은 `PROCESSING` 을 보여주고 목록 조회로 상태를 갱신해야 한다.
  - 워커가 꺼져 있으면(`PUBLISH_WORKER_ENABLED=false`) 예약이 등록만 되고 실행되지 않는다.
- 후속 제약:
  - **`@EnableScheduling` 이 없으면 워커가 아예 돌지 않는다** — 예약 발행이 조용히 죽는다.
  - `Replicas: 2` 에서 두 인스턴스의 워커가 같은 항목을 집을 수 있으므로
    **원자적 선점이 필수다** ([ADR-0015](2026-07-29-atomic-queue-claim.md)).
  - 처리 중 인스턴스가 죽으면 항목이 RUNNING 으로 멈추므로 회수(reclaim) 장치가 필요하다.
