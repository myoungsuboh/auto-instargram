# ADR-0007: 갱신 토큰은 JWT 가 아닌 불투명 난수 + DB 해시

- 기록일: 2026-07-29 12:32
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: [1_spack.md](../../1_spack.md) (직접 규정 없음 — skills 규칙에서 파생)
- 관련 plan: [00-ORCHESTRATOR.md — Phase 2 Task 2.1](../../00-ORCHESTRATOR.md)
- 선행 결정: [ADR-0005](2026-07-29-dashboard-login-added.md), [ADR-0006](2026-07-29-auth-token-transport.md)

## 맥락 (Context)

[skills/security/JWT-authn-authz.md](../../skills/security/JWT-authn-authz.md) 규칙 2 는
"Access Token 만료 15분 이하 + Refresh Token 으로 자동 갱신"을 요구한다.
액세스 토큰은 JWT 로 만들었으므로 갱신 토큰도 JWT 로 만드는 것이 자연스러워 보이지만,
그러면 **로그아웃이 실제로 동작하지 않는다** — JWT 는 자체 완결적이라 서버가 폐기할 수단이 없다.
7일 수명의 갱신 토큰이 유출되면 7일 내내 유효하다.

## 결정 (Decision)

갱신 토큰은 256비트 불투명 난수로 발급하고, DB 에는 그 SHA-256 해시(64자)만 저장해 대조한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 불투명 난수 + DB 해시 | 폐기·회전이 실제로 동작(로그아웃, 탈취 대응). DB 유출 시에도 해시만 있어 로그인 불가 | 매 갱신마다 DB 조회 1회. 테이블 1개 추가 | **채택** |
| 갱신 토큰도 JWT (무상태) | DB 조회 불필요, 확장 쉬움 | 폐기 불가 → 로그아웃이 형식적으로만 동작. 유출 시 만료까지 방치 | 기각 |
| 불투명 난수 + 원문 저장 | 구현이 가장 단순 | DB 유출이 곧 계정 탈취. 비밀번호를 평문 저장하는 것과 같은 급의 실수 | 기각 |
| 원문을 BCrypt 로 해싱 | 비밀번호와 같은 수준의 방어 | 이미 256비트 고엔트로피 난수라 무차별 대입이 불가능해 느린 해시가 무의미하고, 매 요청 검증에 수백 ms 를 낭비한다(POL-04 위협) | 기각 |

JWT 라이브러리 자체는 `io.jsonwebtoken:jjwt` 0.12.6 을 액세스 토큰용으로 채택했다
(Java 표준격 구현, 공통 규칙에 따라 버전 핀 + 레지스트리에서 실재 확인).

## 근거 (Rationale)

"로그아웃이 진짜로 세션을 끊는가"를 기준으로 갈랐다. 무상태 JWT 의 확장성 이점은
이 서비스 규모(3_architecture.md: Replicas 2, 운영 도구)에서 실익이 없고,
폐기 불가라는 대가는 보안상 받아들일 수 없었다.
해시 알고리즘을 BCrypt 가 아니라 SHA-256 으로 한 것도 같은 실용 기준이다 —
입력이 이미 고엔트로피라 느린 해시가 방어를 더해 주지 않으면서 POL-04(3초) 예산만 깎는다.

## 영향 (Consequences)

- 긍정: 로그아웃이 해당 계정의 유효 토큰을 전부 폐기한다(실측: 10건 폐기 확인).
  갱신 시 회전하므로 유출된 토큰의 수명이 다음 갱신까지로 줄어든다.
  폐기된 토큰이 재사용되면 탈취 신호로 보고 그 계정의 모든 세션을 끊는다.
- 트레이드오프/비용: 갱신마다 DB 조회 1회. `auth_refresh_tokens` 행이 쌓인다
  (감사 추적 목적상 즉시 삭제하지 않음 — 정리 정책은 `_workspace/db_schema.json` 의 retention_policy 참조).
- 후속 제약:
  - **갱신 토큰을 JWT 로 "단순화"하면 로그아웃과 탈취 대응이 조용히 사라진다.** 바꾸지 말 것.
  - 토큰 원문은 쿠키에만 존재한다 — 서버 로그·DB 어디에도 남기지 않는다(POL-05 와 같은 취지).
