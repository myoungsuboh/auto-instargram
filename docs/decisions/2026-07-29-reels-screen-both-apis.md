# ADR-0019: 릴스 화면은 업로드와 토큰 갱신을 모두 제공한다

- 기록일: 2026-07-29 14:55

- 관련 spec: [1_spack.md — §5 Screens SCREEN-04](../../1_spack.md), [3_architecture.md — §5 API↔Service](../../3_architecture.md)
- 관련 plan: [00-ORCHESTRATOR.md — Phase 4 Task 4.2](../../00-ORCHESTRATOR.md)
- 구현: [FE/src/views/ReelsDashboardView.vue](../../FE/src/views/ReelsDashboardView.vue)

## 맥락 (Context)

[1_spack.md](../../1_spack.md) §5 의 SCREEN-04 기재가 서로 어긋난다:

| 항목 | 내용 | 가리키는 API |
|---|---|---|
| 화면 이름 | 릴스 업로드 제어 화면 | API-04 |
| 화면 설명 | Resumable 바이너리 직접 업로드 및 4단계 파이프라인 처리 | API-04 |
| 구현 Story | Story-06.1 | API-04 |
| **호출 API 란** | **API-05 `POST /api/v1/tokens/refresh`** | **API-05** |

이름·설명·Story 셋은 모두 릴스 업로드를 가리키는데 호출 API 란만 토큰 갱신이다.

혼선의 근거가 하나 더 있다 — [3_architecture.md](../../3_architecture.md) §5 매핑 표에서도 두 API 의 설명이 서로 바뀌어 있다:

- "POST /api/v1/reels/upload — **SecurityCredential Aggregate 토큰 교환 및 갱신 담당**" (릴스 업로드에 토큰 설명)
- "POST /api/v1/tokens/refresh — **릴스 업로드 파이프라인 실행** 및 관련 비즈니스 로직 처리 담당" (토큰 갱신에 릴스 설명)

즉 두 문서에서 API-04·API-05 가 체계적으로 뒤바뀐 흔적이 있다.
[IMPLEMENTATION-CHECKLIST.md](../../IMPLEMENTATION-CHECKLIST.md) 도 `(→ API: API-05)` 로 적고 있어,
어느 쪽을 따르든 다른 쪽 기재를 어기게 된다.

## 결정 (Decision)

**둘 다 넣는다.** 릴스 업로드를 주 기능으로 배치하고(이름·설명·Story 를 따름),
토큰 갱신도 같은 화면에 둔다(체크리스트의 API-05 지정을 따름).
**사용자 확정 결정**(2026-07-29).

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 둘 다 넣기 | 명세의 모든 기재를 동시에 만족한다. 실사용 흐름과도 맞다 — 릴스를 올리려면 인스타그램 토큰이 유효해야 하므로 같은 화면에서 갱신하는 게 자연스럽다 | 한 화면에 두 기능이 있어 목적이 약간 흐려진다. 두 API 의 권한이 달라(운영자 vs 관리자) 화면에서 구분해야 한다 | **채택** |
| 체크리스트대로 API-05 만 | 체크리스트에 문자 그대로 부합 | 화면 이름이 "릴스 업로드 제어 화면"인데 릴스를 올릴 수 없다. API-04 는 화면 없이 남아 사용자가 쓸 방법이 없다 | 기각 |
| 이름·설명대로 API-04 만 | 화면 성격이 가장 일관됨 | 체크리스트의 "→ API: API-05" 를 만족하지 못해 최종 감사에서 미이행으로 남는다 | 기각 |
| 화면을 두 개로 분리 | 각 화면의 목적이 명확 | 명세에 없는 5번째 화면을 발명하는 셈. 명세는 화면 4개를 규정한다 | 기각 |

## 근거 (Rationale)

ADR-0003·0006 과 같은 패턴이다 — **문서들이 서로 다른 것을 요구할 때, 양쪽을 동시에
만족시키는 구성이 있으면 그것을 택한다.** 어느 한쪽을 버리면 반드시 다른 문서를 어긴다.

실사용 관점에서도 합리적이다. 릴스 게시는 유효한 인스타그램 토큰을 전제하고,
토큰이 만료되면 게시가 실패한다. 게시 화면에서 토큰 상태를 다룰 수 있는 것은 오히려 편의다.

명세 해석이 갈리는 지점이므로 추측하지 않고 사용자에게 세 안을 제시해 확정받았다.

## 영향 (Consequences)

- 긍정: 체크리스트의 SCREEN-04 항목과 API-04·API-05 항목이 모두 실제 화면에서 이행된다.
  운영자가 릴스를 올리고, 관리자가 같은 화면에서 토큰을 갱신할 수 있다.
- 트레이드오프/비용:
  - 두 기능의 권한이 다르다(API-04 운영자 이상, API-05 관리자만). 화면은 관리자가 아니면
    토큰 갱신 영역을 안내 메시지로 대체한다 — 다만 이는 **편의일 뿐 보안 장치가 아니다**
    (SKL-AUTHN-AUTHZ 규칙 3: 진짜 차단은 서버가 한다).
- 후속 제약:
  - **API-05 응답의 장기 토큰을 화면에 표시하지 않는다.** 서버가 이미 암호화 저장했으므로
    사용자가 볼 이유가 없고, 표시하면 화면 공유·스크린샷으로 새는 경로가 생긴다(POL-05 의 취지).
    만료까지 남은 기간만 알려준다.
  - 단기 토큰 입력란은 `type="password"` + `autocomplete="off"` 로 둔다.
