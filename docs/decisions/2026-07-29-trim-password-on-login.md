# ADR-0020: 로그인 시 비밀번호의 앞뒤 공백을 제거한다

- 기록일: 2026-07-29 15:10
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: [1_spack.md](../../1_spack.md) (직접 규정 없음 — 로그인은 ADR-0005 로 추가된 기능)
- 선행 결정: [ADR-0005](2026-07-29-dashboard-login-added.md), [ADR-0006](2026-07-29-auth-token-transport.md)
- 구현: [FE/src/views/LoginView.vue](../../FE/src/views/LoginView.vue)

## 맥락 (Context)

Phase 4 검증 중 **실제로 발생한 문제**다. 사용자가 문서에 적힌 비밀번호로 로그인했는데
`INVALID_CREDENTIALS`("아이디 또는 비밀번호가 올바르지 않습니다")만 반복됐다.

서버 로그로 범위를 좁혔다:

```
15:03:03  로그인 실패 — 비밀번호 불일치 'admin'     ← 계정은 찾음, 비밀번호만 불일치
15:06:18  로그인 성공 — 'admin'                      ← 같은 조합을 curl 로 보내면 성공
```

변형별 실측 결과 — 아래 모두 **구별 불가능한 동일 응답**을 낸다:

| 보낸 값 | 결과 |
|---|---|
| `Admin!2026Local` | 200 성공 |
| `Admin!2026Local ` (뒤 공백) | 401 INVALID_CREDENTIALS |
| ` Admin!2026Local` (앞 공백) | 401 INVALID_CREDENTIALS |
| `admin!2026Local` (대소문자) | 401 INVALID_CREDENTIALS |

즉 붙여넣기로 딸려온 공백이 유력한 원인인데, **그 문자는 입력란에서 보이지 않는다.**
사용자는 올바른 값을 넣었다고 믿으면서 같은 실패를 반복하게 된다.

## 결정 (Decision)

로그인 화면에서 비밀번호를 서버로 보내기 전에 앞뒤 공백을 제거한다({@code password.trim()}).
추가로 실패 시 자가 진단 항목(대소문자 · 한영/Caps Lock · 붙여넣기 공백)을 안내한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 화면에서 앞뒤 공백 제거 | 붙여넣기 사고가 사라진다. 이 시스템에서는 잃는 것이 없다(아래 근거) | 일반론으로는 "비밀번호를 변형한다"는 점이 보안 검토에서 지적될 수 있다 | **채택** |
| 서버에서 제거 | 모든 클라이언트에 일괄 적용 | API 클라이언트가 보낸 값을 서버가 임의로 바꾸는 것은 계약 위반에 가깝다. 프로그램 클라이언트는 자기 입력을 통제할 수 있고 통제해야 한다 | 기각 |
| 아무것도 하지 않고 안내만 추가 | 비밀번호를 전혀 건드리지 않는다 | 안내를 읽어야 해결된다. 보이지 않는 문자를 사용자가 직접 찾아 지워야 하는데, 입력란에서는 확인할 방법이 없다 | 기각(안내는 함께 채택) |
| 공백이 감지되면 경고 표시 | 변형 없이 알려줄 수 있다 | 입력값의 성질을 화면이 알려주는 셈이라 어깨너머 노출에 취약하고, 결국 사용자가 손으로 고쳐야 한다 | 기각 |

## 근거 (Rationale)

일반론으로 비밀번호 trim 은 권장되지 않는다 — 앞뒤 공백이 의미를 갖는 비밀번호를 쓸 수 없게 되기 때문이다.
**그러나 이 시스템에서는 그런 비밀번호가 존재할 수 없다:**

1. 계정은 {@code AccountSeeder} 가 환경변수 `SEED_ADMIN_PASSWORD` / `SEED_OPERATOR_PASSWORD`
   에서만 만든다 (비밀번호 변경·가입 기능이 없다).
2. 그 값은 스프링의 properties 파서를 거치는데, **파서가 이미 앞뒤 공백을 제거한다.**

즉 저장된 해시는 언제나 앞뒤 공백이 없는 문자열의 해시다.
따라서 trim 은 로그인 가능한 조합을 <b>하나도 줄이지 않는다</b> — 키 공간이 좁아지지 않는다.
반대로 trim 하지 않으면, 보이지 않는 문자 때문에 정당한 사용자가 잠기는 일만 생긴다.

서버가 아니라 화면에서 처리한 이유: 서버가 받은 값을 바꾸면 API 계약이 흐려진다.
공백은 "사람이 붙여넣다가 생기는 사고"이므로 사람이 쓰는 입구에서 처리하는 것이 맞다.

## 영향 (Consequences)

- 긍정: 붙여넣기로 인한 로그인 실패가 사라진다. 실패 시 사용자가 스스로 원인(대소문자·IME)을
  좁힐 수 있다.
- 트레이드오프/비용:
  - 앞뒤 공백이 있는 비밀번호로는 로그인할 수 없다 — 위 근거대로 그런 계정이 존재할 수 없으므로
    현재 실질적 손실은 없다.
  - 서버는 여전히 받은 값을 그대로 검증한다 — curl 등으로 공백을 보내면 실패한다(의도된 동작).
- 후속 제약:
  - **비밀번호 변경·회원가입 기능을 추가한다면 이 전제가 깨진다.** 사용자가 임의 비밀번호를
    직접 정할 수 있게 되면 앞뒤 공백이 의미를 가질 수 있으므로, 그때는 이 결정을 재검토하고
    "가입 시에도 trim" 처럼 양쪽을 일치시켜야 한다.
  - 아이디는 trim 하되(이미 `v-model.trim`) **대소문자는 구분한다** — 계정을 찾는 키이므로
    임의로 소문자화하면 다른 계정과 충돌할 수 있다.
